## Vulkan evidence

The focused job used the pinned shader tools and Mesa llvmpipe. Its retained
CTest log reports passing `TEST_VulkanShaderAbi`, `TEST_VulkanCompute`, and
`TEST_VulkanFrameLoop`, with no validation-error/VUID markers.

The native test uses the production VulkanRHI, not a separate swapchain harness.
It exercises selected initialization failures and retry, deferred zero-sized
initialization, bounded frame submission through the presentation path, resize
between 128x256 and 256x128, deferred minimize/restore, and repeated shutdown.
This is native Xcb/WSI execution on a software driver, not a Vulkan Viewer
screenshot or proof of displayed scene frames.

## Limitations

- The new generic resource/upload/readback implementation and its resource
  regression test were developed after this revision and are not verified here.
- Local Windows ABI/compute checks pass on AMD Radeon(TM) Graphics, but the
  production Win32 frame-loop test fails at the surface-capabilities query with
  `VK_ERROR_UNKNOWN`. An independent SDK vkcube run also failed to finish within
  a bounded check. The cause is not established; no driver/display configuration
  was changed. Windows Vulkan WSI is not counted as passed.
- macOS Metal regression success does not verify the Cocoa Vulkan adapter,
  MoltenVK compilation/runtime, or portability fallback.
- Presentation semaphores are indexed by acquired image, separately from frame
  fences. Swapchain retirement currently uses device-idle waits. As explained by
  the [Khronos presentation synchronization guide](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html),
  unextended Vulkan cannot strictly prove presentation-resource retirement with
  those waits alone. Presentation-fence handling remains checkpoint 2 work.
- Shared Vulkan graphics passes, point-shadow execution, Viewer/Billiard Vulkan
  output, ImGui, and MSAA rendering are not established by this foundation.

This record verifies only the tested source revision, not its later
