## Material and portability evidence

- The real scene material upload path generates a complete chain for base-only
  images. Compressed bases are decoded through the existing shared
  `passthrough.vert` and `texture.frag` stages into filterable storage before
  the existing checked linear mip generation.
- GPU readback covers BC1 quadrant orientation, UNORM values without an extra
  gamma decode, averaged intermediate/final levels, signed BC4 and floating
  BC6H storage, and padded non-square RGB input. Supplied chains, including
  partial chains, remain unchanged; scalar fallbacks and GUI image creation
  retain their single-level behavior. Prefiltered environment upload is
  untouched.
- The negative control restored the original material upload call and failed
  on the missing BC mip chain. The fixed path passed the local six-test suite
  on the Windows AMD device and both explicit Vulkan CI suites.
- Linux passed shader ABI, compute, resources, pipelines, graphics, GUI, and
  native frame-loop tests. Native coverage retains main/secondary resize,
  secondary destruction/recreation, renderer lifetimes, maintenance1 present
  retirement, and framebuffer byte-count/color/orientation checks.
- Stable MoltenVK passed shader ABI, compute, resources, pipelines, graphics,
  and GUI tests with validation enabled and an explicitly selected ICD. Its
  validation-library lookup is scoped to the test process. No Vulkan native
  frame-loop test or Vulkan WSI application was run on macOS.
- MoltenVK ignores `VkAllocationCallbacks`. GUI partial-initialization rollback
  and retry therefore also use an ImGui allocator failure after backend
  context binding on every platform. Windows/Linux retain the original
  Vulkan host-allocation rejection probe; macOS explicitly reports that
  unsupported injection mechanism rather than claiming it ran.

The Linux Vulkan test log had zero `Validation Error`/`VUID-` markers and one
expected `Vulkan validation: VK_ERROR_OUT_OF_HOST_MEMORY` diagnostic from the
deliberately failing allocator, with no other validation callbacks. The
MoltenVK test log had zero `Validation Error`/`VUID-` markers. Both real Vulkan
application logs had zero validation callbacks and zero missing/invalid
`Materials/` diagnostics.

## Limits and follow-ups

- Windows Vulkan WSI and native MoltenVK, floating-window input/lifecycle, and
  Retina scaling remain unverified. The local Windows SDK 1.2.182 cannot run
  the strict native frame loop; local instance enumeration also did not
  expose surface-maintenance1. Correction from a subsequent tagged-source
  recheck: stable MoltenVK v1.4.2 does declare KHR/EXT
  surface/swapchain-maintenance1; the earlier absence claim was incorrect.
  This revision ran only its headless tests and does not establish those
  native features. No development runtime has been authorized or substituted.
- Linux lavapipe/Xcb is software reference coverage, and the macOS Vulkan
  device is paravirtual. Neither establishes physical hardware-driver parity.
  Xcb platform input still disables ImGui multi-viewports; directly driven
  secondary-renderer callbacks do not establish floating-window input support.
- Native presentation still requires maintenance1 fences. There is no
  device-idle retirement fallback. Secondary presents remain synchronous
  scoped-fence waits; no general device-loss recovery is claimed.
- Capture requires transfer-source swapchain support and an RGBA8/BGRA8 UNORM
  presentation surface. Vulkan application artifacts are PPM, not PNG.
- The renderer's existing uniform-range, shadow-filtering, scene-stream, and
  unsupported-format restrictions remain in the
  [implementation plan](../architecture/vulkan-rhi-implementation-plan.md#known-limitations-and-follow-ups).

Shared scene/pass/UI scheduling and HLSL remain in use. No Vulkan-specific
scene shader copy, alternate material cooker, submodule change, PR, or merge
was introduced by this checkpoint continuation.
