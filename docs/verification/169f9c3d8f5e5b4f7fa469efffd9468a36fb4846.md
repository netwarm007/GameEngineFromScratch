## Windows native coverage: how it was established

Two environment facts blocked Windows native OpenGL/Vulkan startup until this
revision; both are now resolved in the CI matrix step:

- **No enumerable interactive desktop.** The executor runs the build elevated
  in a service session; `FindWindowW` cannot locate the Viewer window, so GDI
  client-area capture is not viable. The Win32 OpenGL host therefore gained a
  `GEFS_SCREENSHOT_PATH` self-capture: after a 45s render gate (or a
  `GEFS_SCREENSHOT_WAIT_FOR` marker) the main loop reads the presented front
  buffer with `glReadPixels`, writes an 8-bit RGB PNG through zlib, and retires
  the application — matching the D3D12/Vulkan self-capture contract. The PNG
  writer logic was round-trip verified against `compare_captures.py`'s decoder.
- **Elevated loader ignores ICD env vars.** `VK_LOADER_DEBUG` showed the Vulkan
  loader ignores `VK_ICD_FILENAMES`/`VK_DRIVER_FILES` under elevated
  permissions and reads only the registry, so the lavapipe ICD was never
  discovered (missing `VK_KHR_get_surface_capabilities2`). The matrix now
  registers the lavapipe ICD json in the 64-bit view of
  `HKLM\SOFTWARE\Khronos\Vulkan\Drivers` (the key the loader scans) and deploys
  the ICD DLL together with its sibling DLLs next to the executable. The
  system loader is used (the SDK installer refreshes System32 to 1.4.363.1);
  an opt-in `GEFS_VULKAN_LIBRARY` override can point at an alternate runtime.

## Remaining scope and limitations

- M2.6 stage 1 covers the **Viewer** startup matrix only. The Billiard
  per-backend startup matrix, `--list-rhi`/error-path native smoke, and
  migration of the specialized `verify_vulkan_shader_abi` coverage into the
  platform jobs remain M2.6 scope; the specialized job is retired only after
  equivalent coverage is verified.
- Cross-backend tolerances are calibrated to software-rasterizer variation, not
  pixel-exact equivalence; they assert scene/layout agreement, not identical
  rasterization across backends.
- Linux runtime selection retains the SDL OpenGL host (the XCB host has no
  ImGui platform input backend); XCB ImGui parity remains the prerequisite for
  the agreed XCB-only host, tracked in the roadmap's Known limitations.
