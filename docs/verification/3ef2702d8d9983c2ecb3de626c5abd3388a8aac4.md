## New native evidence

The existing frame-loop regression now uses Cocoa NSWindows with CAMetalLayer
surfaces on macOS, with backing-pixel size queries and layer sizes updated at
resize. The test reuses the same production Vulkan RHI and GUI renderer as the
Windows/Xcb path; no alternate renderer or weaker presentation path was added.

On stable MoltenVK the native regression passed:

- Injected surface/device-stage initialization failure, rollback, and retry.
- Twenty native frame submissions, resize, deferred minimize/restore, aborted
  acquired recording, and repeated shutdown.
- Main/secondary GUI composition, engine texture identities, main/secondary
  resize, secondary destruction/recreation, two renderer lifetimes, and cleanup.
- Strict maintenance-aware presentation-fence retirement for both main and
  secondary swapchains; the native instance enabled
  `VK_EXT_surface_maintenance1` and the RHI's device/feature gate succeeded.
- Application-only GUI framebuffer readback with exact PPM dimensions/byte
  count, expected image channel values, top-left placement, and background.

All seven standalone tests passed on both explicit Vulkan CI paths: shader
ABI, compute, resources, pipelines, graphics, GUI, and native frame loop.
The portable ImGui allocator rollback probe remains active on macOS, which
does not claim support for Vulkan allocation-callback fault injection.

MoltenVK tests reported zero validation callbacks and zero
`Validation Error`/`VUID-` markers. Linux tests had zero such markers and only
the expected host-allocation rejection diagnostic. All four real Vulkan
application logs had zero validation callbacks and zero missing/invalid
scene-material diagnostics.

## Remaining blockers and minimal environment choices

- **Windows Vulkan:** Direct calls to the installed loader found no instance
  maintenance extensions, and no swapchain-maintenance1 extension on the AMD
  adapter or either Dozen adapter. The local AMD driver is
  `32.0.21030.2001`; SDK `1.2.182.0` additionally fails the native regression
  explicitly at its header gate. The six supported local tests passed and
  the Windows native test target rebuilt successfully; its native run still
  failed the capability gate, so there is no Windows WSI acceptance.
  Supply a Windows machine/runner whose instance and chosen device expose the
  matching KHR/EXT surface/swapchain-maintenance1 pair and
  `swapchainMaintenance1=true`. A matched stable SDK/validation installation
  such as LunarG's currently advertised Windows `1.4.363.1` addresses the SDK
  portion only; it cannot add absent driver capabilities. No untested driver
  version is claimed to solve this. Driver/system installation changes need
  separate authorization; an already-capable environment needs no engine
  dependency replacement.
- **Physical Retina and floating input:** Supply an accessible interactive
  Retina Mac, preferably with both 1x and 2x displays. The already-tested stable
  MoltenVK 1.3.0 / Vulkan 1.4.315 toolchain is a reproduction baseline, not a
  requirement to downgrade another machine. Run the native tests and actual
  applications, then verify detach/redock, cross-display resize/scaling,
  keyboard/pointer focus/input, close/recreate, and saved layouts. The current
  native regression directly drives renderer callbacks; it does not establish
  those interactive input contracts. Scale-1 paravirtual WSI is not physical
  Retina acceptance.
- No development MoltenVK, production dependency replacement, device-idle
  presentation-retirement fallback, default-backend change, PR, or merge was
  introduced. The earlier claim that stable MoltenVK lacked maintenance1
  declarations was corrected in the preceding revision's record; this native
  run supplies the runtime evidence that declarations alone could not supply.
