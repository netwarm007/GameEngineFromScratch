## Inspected Billiard captures

The three `billiard-screenshots/billiard-after.png` artifacts were inspected.
Metal and D3D12 show the table; the D3D12 image includes the existing hover
magnifier. The Linux image shows the UI but an empty, gray Viewer area despite
the successful screenshot step, so it cannot establish a Linux visual result.
Viewer screenshots were not inspected for this diagnostic.

For the `[700, 330, 750, 380)` cloth patch, mean display-encoded PNG RGB is:

| Capture | Mean RGB |
| --- | --- |
| Baseline Linux OpenGL, job 4410 | (58.33, 189.19, 101.57) |
| Baseline macOS Metal, job 4411 | (45.16, 165.52, 81.06) |
| Experiment macOS Metal, job 4421 | (56.75, 188.45, 100.13) |
| Baseline Windows D3D12, job 4412 | (56.71, 188.68, 100.22) |
| Experiment Windows D3D12, job 4420 | (56.71, 188.68, 100.22) |

Disabling the Lamp shadow raises the macOS green mean by 22.93, reducing the
previous 23.67 difference from the baseline Linux green mean to 0.74. The
macOS table body and floor also become brighter; a sky patch remains unchanged.
This identifies the Metal Lamp shadow path as the cause of most of the
observed patch difference, but does not identify which shadow implementation
defect is responsible or verify a correct shadow fix. PNG means are not
linear-light values and do not establish pixel equivalence.

Linux baseline job 4410 reports the missing `shadowmap_omni.geom.glsl` shader;
the pipeline manager can substitute another pipeline after registration fails.
Thus the baseline Linux image is not evidence of correct point shadows. The
same missing shader is reported in experiment job 4419. The blank experiment
capture needs separate investigation before comparing Linux with shadows off.

Linux used software OpenGL; hardware GPUs, other backends, and disabled Android
were not verified. These results verify only the diagnostic revision above,
not the current branch, a merge revision, or a future fix. The passing jobs do
not constitute visual acceptance of the blank Linux capture.
