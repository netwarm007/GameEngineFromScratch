# Windows CI compiler caching and Ninja build: verification

## Tested revision and scope

- Tested source: `e8eaac18e98fe5398859cd162458d2f4e2fdef63`.
- Branch: `feat/runtime-rhi-build`.
- Full CircleCI [pipeline 1085](https://app.circleci.com/pipelines/github/netwarm007/GameEngineFromScratch/1085)
  ([run](https://app.circleci.com/pipeline/dbd5e818-9493-4dc9-817d-7c327c8211a9)).
- Workflow: `build-and-test`, `3170a3fa-c36e-477b-a1fe-32af677d9ab4`, successful.

This revision changes CI and one MSVC flag guard only; no engine, rendering,
shader, or test source changed. It verifies that the Windows CI speedup work
builds and passes the complete configured suite on every enabled platform:

- Windows engine builds use Ninja under `vcvars64` with sccache as the C/CXX
  compiler launcher; Debug uses embedded debug information (`-Z7`) so MSVC
  objects are cacheable. Both Windows ctest steps run under `vcvars64` because
  `TEST_DesktopApplications` configures its fixture with the engine's generator
  and compiler.
- `/MP` is added only for the Visual Studio generator (`CMakeLists.txt`); under
  Ninja it oversubscribed cores and contended on the shared `/Fd` PDB (C1041),
  and sccache cannot cache `/MP` compilations. Local Visual Studio builds keep
  `/MP`; developer presets are unchanged.
- The Windows and Unix dependency cache keys no longer hash `config.yml`, so
  CI-only edits stop invalidating dependency caches. Build scripts, submodule
  revisions, and toolchain remain hashed.
- Linux/macOS pass the ccache launchers explicitly via `-D`. Correction to the
  message of `ab8e104a`: CMake has initialized `CMAKE_<LANG>_COMPILER_LAUNCHER`
  from the environment since 3.17, so the previous env-var configuration was
  already effective; the explicit flags are equivalent, not a Unix fix.

## Compiler-cache evidence (Windows, job 4852)

- Debug `Build Engine`: sccache 443 compile requests, 443 executed, 0 cache
  errors, 0 non-cacheable compilations, 95 MiB cached.
- After `Build Engine (Release)`: 886 cumulative requests, 0 errors, 0
  non-cacheable, 113 MiB cached.
- All dependency build steps restored from cache (each under 20 s), confirming
  the stabilized dependency cache key.
- This run was cold for sccache: branch runs restore but do not save the
  compiler cache (master-only save, mirroring the existing ccache pattern), so
  every request was a miss. Hit-rate speedup is therefore not yet demonstrated;
  it begins after the first master run saves `sccache-windows-v1`.

## Limitations and follow-ups

- sccache was cold on this branch run; warm-cache Windows duration is projected
  to drop substantially (engine Debug+Release ~12.9m here) but is unmeasured
  until a master run populates the cache.
- Intermediate pipelines are not acceptance evidence for this revision: 1076
  and 1078 passed with sccache inactive (VS generator ignores
  `COMPILER_LAUNCHER`; the `_DEBUG`-suffixed format variable does not exist),
  1082 failed with C1041 (`/MP` + shared PDB under Ninja), and 1083 failed in
  `TEST_DesktopApplications` (fixture try-compile lacked the MSVC environment).
  Each cause is fixed in this revision's history.
- The Windows CI generator now differs from the local Visual Studio preset;
  both paths are exercised only in their respective environments.
- `quick-*` results never count as acceptance; none are claimed here.
